## 2. 运行时声学事实（语义安全论证的地基，全部已实证）

1. **GC 只在分配中触发**：唯一分配入口 `il2cpp_gc_alloc` / `il2cpp_gc_alloc_size`
   （gc.cpp:1198/1210）→ `AllocCore`（gc.cpp:1146，collect-then-retry 在 :1168）。
   生成代码/运行时所有托管分配（newobj/newarr/ldstr/box/delegate_new/string 族）
   都经此路径。→ **一个执行期间无任何分配（本方法 + 传递闭包）的方法不可能触发 GC。**
2. **分配永不返回 null**：`AllocCore` 对合法 klass 的每个出口要么返回有效块，要么
   `FailLoud` abort（段分配失败 gc.cpp:334、块表满 gc.cpp:393、forward map 满 :999）。
   `klass == nullptr` 才返回 null——生成代码恒传 `&<T>_class`。→ **newobj/newarr/
   ldstr/delegate_new/box 结果必非空**（K 集加入点的声学依据）。
3. **`il2cpp_null_check` = fprintf + abort()**（object.cpp:53-61），零分配、零异常
   对象。→ 字段访问发射的检查调用是 GC-free 的。
4. **`il2cpp_throw_new` = C++ `throw DotNetException`**（exception.cpp:28-31）；
   `DotNetException : std::exception`（il2cpp_exception.h:41）纯 C++ 对象，无 GC
   分配。→ throw/checked_div/checked_rem/数组边界检查的失败路径 GC-free。
5. **`il2cpp_write_barrier` = 块表线性查 + 置卡**（gc.cpp:1059-1090），零分配。
6. **帧 pop = RAII 析构**（il2cpp_frame.h:61-63）：每返回路径恰好 1 次 pop（正常返回
   与异常展开同路径），`prev != nullptr` 守卫幂等。→ **O4 已由 RAII 解决**（旧
   add/remove root range 协议的每-return remove 已不存在），实施只需钉死测试。
7. **GC 扫描范围**：静态根 + root range + 帧栈（gc.cpp:585/682 走
   `il2cpp_frame_top()`）；不扫任意 C++ 栈。→ 未注册帧的方法，其 C++ 局部/参数在
   收集器不可见——这正是跳过帧时必须证明"该窗口无 GC"的原因。

## 3. O1：GC-free 方法跳过帧根注册

### 3.1 形态变化

方法 M 的帧从：
```cpp
void* __frameRefs[] = { (void*)&arg0, (void*)&loc1, ... };   // 7 行序言
il2cpp::Il2CppFrame __frame = { nullptr, nullptr, nullptr, 0 };
__frame.methodName = "..."; __frame.refs = ...; __frame.refCount = N;
il2cpp::il2cpp_frame_push(&__frame);
<body>
// (RAII 析构隐式 pop)
```
变为**零输出**（整个序言消失；body 不变）。

### 3.2 判定算法（IR 级，CodeGenerator.Generate 内）

```
frameNeeded = refLocals.Count > 0 && stmts.Any(MayTriggerGc)
```
`MayTriggerGc(Stmt/Expr)` 递归（覆盖 AssignStmt.Value / CallStmt.Args /
FieldAssignStmt.Object+Value / BranchStmt.Condition / RetStmt.Value / ExprStmt.Value）：
- 恒真：`NewObjExpr`、`DelegateNewExpr`、`StringConstExpr`（→ string_new 分配）、
  `MarshalUtf8Expr`（保守）、`VirtualCallExpr`、`DelegateInvokeExpr`、任意
  `CallExpr`/`CallStmt`（除下方白名单）。
- 恒假：`NullExpr`、`LocExpr`、`IntConst`、`StaticFieldExpr`、`LocAddrExpr`、
  `FieldExpr`/`FieldAddrExpr`/`FieldAssignStmt`（发射只含 null_check +
  write_barrier，均 GC-free，§2.3/§2.5）。
- 调用白名单（发射后调用目标为 GC-free 运行时函数，按 Function 前缀）：
  `throw_`（§2.4）、`ldlen_`/`ldelem_`/`stelem_`（get_length 纯读 / get_elem_ptr
  边界检查失败=abort 或 C++ throw，零分配）、`unbox_`、`isinst_`/`castclass_`
  （typecheck 纯指针行走）、`pinvoke_utf8_free`、`capture_last_error`。
  其余（`call_`/`vcall_`/`dinvoke_`/`vctor_`/`box_`/`newarr_`/`ensure_cctor_`/
  icall）一律**保守视为可能分配**。

### 3.3 语义安全论证

- GC 只发生在分配内（§2.1）。M 被判定 GC-free ⟺ M 及其全部被调函数（按上述保守
  白名单）在任何路径上都不调用分配入口 → M 在栈期间不可能发生 GC → M 的引用局部/
  参数/this 无需根化（收集器不扫 C++ 栈，§2.7——若 M 注册了帧则会被扫，但不存在
  GC 窗口，注册是纯浪费）。M 返回后其局部消亡，无残留。
- 例外/诊断路径：null_check 的 abort 与 throw_new 的 C++ throw 均不触发 GC（§2.3/§2.4）。
- 帧的 StackTrace 用途（exception.cpp:86 行走帧栈报告方法名）随帧跳过而丢失该方法的
  栈帧名——**诊断弱化，非语义变化**（M 仍正常执行、正常返回；仅未处理异常报告的
  调用栈中缺 M）。披露于 §8。
- 保守边界：`ensure_cctor_` 视为可能分配（注册表静态、实际可能零分配，但为免依赖
  内部实现细节不进入白名单）；catch 处理器语句在 stmts 内，分析天然覆盖。

### 3.4 测试（RED→GREEN）

- `Generate_GcFreeInstanceMethods_SkipFrameRegistration`（props 夹具）：
  AuditFix_Counter.cpp（ctor + Doubled=`_value*2` 纯字段读 + Tag=`return 0`）
  **无 `__frame`/`il2cpp_frame_push`**；AuditFix_SubCounter.cpp 同；AuditFix_Props.cpp
  Main（newobj）**含** `il2cpp_frame_push`。RED：Counter.cpp 现含帧。
- 回归：`Generate_RefParam_IsRegisteredAsFrameRoot`（refarr）必须仍绿——
  ReadViaParam 有 `new Node(i)` 循环 → MayTriggerGc=true → 帧保留。

## 4. O2：temp 合并（StackFold 尾后 pass，IR 级）

### 4.1 Merge A：newobj/委托两代 temp

IR 形态（已实证）：
```
t0 = il2cpp_object_new(&T_class);   (AssignStmt, Value=NewObjExpr/DelegateNewExpr)
T__ctor(t0, ...);                   (CallStmt, Function 前缀 "call_", Args[0]=LocExpr(t0))
loc0 = t0;                          (AssignStmt, Value=LocExpr(t0))   ← 可省略
```
算法（对 stmts 顺序扫描，重建式修改）：
1. 定位 `stmts[i]`：`Target=tX`，`Value` 为 `NewObjExpr` 或 `DelegateNewExpr`；
2. 统计 tX 的全部 LocExpr 出现（递归覆盖所有表达式位置）；
3. 仅接受两种形状：
   - **uses==1** 且唯一用是 `stmts[i+1]` 的拷贝 `locY = tX`（委托形状，无 ctor）；
   - **uses==2** 且 `stmts[i+1]` 是 `call_` 前缀 CallStmt 且 `Args[0]=LocExpr(tX)`，
     `stmts[i+2]` 是拷贝 `locY = tX`（newobj 形状）；
4. 重建：`stmts[i]` 改为 `Target=locY`（Value 不变）；ctor 的 `Args[0]` 改 `locY`；
   删除拷贝语句；`objTypes` 迁移：`objTypes.Remove(tX, out tt)` →
   `objTypes[locY]=tt`（throw 站点类型跟踪不丢，audit H8 回归）。
声学：tX 仅被 ctor 与拷贝引用、定义与使用线性相邻（无 label/分支插入其间的可能，
IL 为 newobj;stloc 连续指令）→ 改名后每条路径行为逐语句相同；locY 的声明/类型推断
由既有 EmitBody 传播式处理（NewObjExpr→"ref"）。

不合并的情形（保持原状，均有测试）：tX 直接被使用（无 stloc）、uses 含其它位置
（如 ctor 参数复用）、System.Exception 的 NullExpr 形状（保守不做）。

### 4.2 Merge B：join 槽均匀拷贝折叠

IR 形态（boxing 三元已实证）：
```
t2 = t0;        // 真臂（RegisterJoin）
t3 = t1;
goto L_110;
L_109:
t2 = t0;        // 假臂（fall-through join 写入）
t3 = 0;
L_110: ...      // 读 t2/t3
```
算法：对每个 temp j（join 槽），若**全部** `AssignStmt{Target=j}` 的 Value 都是
`LocExpr(s)`（同一 s），且 s 恰有 **1 个**赋值语句（单赋值 temp/局部），则：
把全部 `LocExpr(j)` 读替换为 `LocExpr(s)`，删除 j 的全部赋值。
（j 无 objTypes 条目——join 槽由 RegisterJoin 命名、从不直接承接 newobj——无需迁移。）
s 的赋值语句唯一 + 栈纪律（分支指令上的栈值必先于其入栈指令、同一块内线性执行，
或经 join-restore 恢复=多赋值槽被单赋值检查排除）⟹ 每条到达 j 读取的路径都在
**当次迭代内**先执行了 `j = s` 且 s 在该写点与读点之间不被重赋值（s 的唯一
AssignStmt 按栈纪律恒先于同迭代的 j 写）。折叠后读 s ≡ 读 j。

不折叠的情形（保持原状，有测试）：混合源（`t3 = t1` vs `t3 = 0`）、源为多赋值槽。

## 5. O3：null_check 消除（known-non-null 集）

### 5.1 形态变化

```
((Point*)il2cpp_null_check((Il2CppObject*)(loc0)))->X + ((Point*)il2cpp_null_check((Il2CppObject*)(loc0)))->Y
→ ((Point*)((Il2CppObject*)(loc0)))->X + ((Point*)((Il2CppObject*)(loc0)))->Y     // 同语句内第 2 次跳过
```
（cast 保留——成员访问需要具体 struct 指针；仅去掉检查包装。）

### 5.2 K 集规则（EmitBody 主循环持有 `HashSet<string> knownNonNull`，语句序维护）

加入（语句发射后）：
- `AssignStmt target = NewObjExpr/DelegateNewExpr` → add(target)（§2.2 永非空）。
- `AssignStmt target = LocExpr(s)` 且 s ∈ K → add(target)（拷贝传播非空性；s 若其后
  被重赋值会先被移除，见下）。
- 检查点发射时：FieldAccess / EmitVirtualCall / DelegateInvoke 的接收者若为
  `LocExpr(s)` 且 s ∈ K → **跳过检查**；否则发射检查并 **add(s)**（检查通过即证明
  非空——跨语句与同表达式内部均适用；C++ 语句顺序执行 + 表达式无副作用树）。
移除（语句发射后）：
- 任何其它 `AssignStmt target=...` → remove(target)（可能写入 null/旧值）。
- CallStmt 含 `LocAddrExpr(n)` 实参 → remove(n)（被调者可能经引用写 n）。
清空：
- `LabelStmt`（多入边汇合，交集未知——清空是保守且充分的）。
- `BranchStmt`（分支前的检查事实可能未在另一臂执行——**必须清空**，否则前臂事实
  泄漏进后臂造成误消）。
- `OpenCatch` 进入 handler 时（try 内语句可能未完成——如 `t = a/b` 抛除零，t 的
  K 事实在 catch 内不成立）。
分支守卫（发射后清空再定向加入）：fall-through 非空事实——
- 条件为 `Ceq(LocExpr(s), IntConst(0))`（brfalse s）→ add(s)；
- 条件为 `Ceq(LocExpr(s), NullExpr)`（brtrue s==null）→ add(s)；
- 条件为 `Ceq(Cgt/CgtUn(LocExpr(s), NullExpr), IntConst(0))`（brfalse s!=null）→ add(s)；
- （镜像操作数位置同理；`Not(e)` 在 StackFold 已归一化为 `Ceq(e,0)`——StackFold.cs:1245。）
跳转目标臂（brtrue s / brfalse s==null 的目标块）**不做**（前向标注复杂，放弃，
保守损失可接受——`if (x == null) return;` 守卫风格正是 fall-through 形状，已覆盖）。

finally 重复发射点（CodeGenerator EmitBody 四处）：传**全新空集**（保守）。

附带修复（FieldAssignStmt 现有双发）：`fa.Value` 的表达式当前被 EmitExpr 两次
（:568-569 与 :575）——改为缓存一次发射的字符串复用两行，避免同一表达式两次发射
产生"一检查一不检查"的不一致文本（对合法程序语义相同，但形态不一致）。

### 5.3 语义安全论证

- 消除只发生在 s ∈ K 且 K 的加入点均有证明（newobj 永非空 §2.2；检查通过即非空；
  守卫 fall-through 即非空；拷贝传播由赋值序保证）。K 的移除/清空覆盖全部重赋值
  与汇合路径 → 消除点处 s 确实非空。
- 有效程序（不 deref null）行为逐字节相同；null 接收者程序从"abort 诊断"变为
  "UB/崩溃"——**诊断弱化非语义变化**（M2 本来就 abort 而非 .NET NRE 异常），披露
  于 §8。审计 #4 的推荐语（"同表达式已检查过的接收者，跳过后续 null_check"）与
  本设计一致。
- 接收者非 LocExpr（字段链值如 `loc1->ref1` 的读取结果）不进入 K（无名字）——
  此类检查保留（objects 用例的 ref1 值检查仍存在，仅 loc1 的检查消除）。

## 8. 风险与披露

- **诊断弱化（O3）**：null 接收者程序由 abort 变为 UB。M2 契约本就是"abort 非 NRE"，
  审计 #4 明确推荐该消除；每处消除有 K 集证明（对有效程序零差异）。
- **StackTrace 帧缺失（O1）**：GC-free 方法不再出现在未处理异常的帧栈报告（异常
  路径本来也不经其分配——仅报告缺失，无正确性影响）。
- **保守边界（O1）**：`ensure_cctor_`/icall 一律视为可能分配——静态字段密集叶方法
