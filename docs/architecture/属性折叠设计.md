# 属性折叠设计（简单 accessor inlining）

> 依据：docs/REQUIREMENTS.md 铁律 2j——简单属性（get/set 直接返回/设置字段）
> **必须折叠为字段访问，不编译为函数**（避免调用开销）。折叠安全条件
> （铁律原文）：① 属性方法非虚；② 字段在同类内；③ 方法体确认为简单
> accessor 形态（解码验证，不是猜测）。纯 AOT 转译期优化，不破坏语义。
>
> 配套背景：生成方法统一 `IL2CPP_NOINLINE`（src/il2cppc/Emit/MethodEmitter.cs:13，
> 帧记录/StackTrace 铁律禁内联）——因此**属性折叠是"禁内联"约束下唯一合法的
> accessor 消除手段**：不加折叠，每个 `obj.X` 都是真实函数调用。

---

## 1. 目标形态

| 属性 | IL 体（解码后指令序列） | 折叠后生成 | 不折叠（现状） |
|---|---|---|---|
| `int X { get { return _x; } }` | `ldarg.0; ldfld _x; ret` | `obj->X_f` 直接读字段 | `int32_t t = {Type}_get_X_hash(obj);` 函数调用 |
| `void X { set { _x = value; } }` | `ldarg.0; ldarg.1; stfld _x; ret` | `obj->X_f = value;` 直接写字段 | `{Type}_set_X_hash(obj, value);` 函数调用 |
| `static int S { get; }`（静态） | `ldsfld _s; ret` | `{Type}_sf_S;` 直接读静态字段 | 函数调用 |
| `static int S { set; }`（静态） | `ldarg.0; stsfld _s; ret` | 直接写静态字段 | 函数调用 |

性能差异量级（x64，-O2）：

- 不折叠：`call` +（NOINLINE 屏障：跨函数调用无法内联传播，参数/返回压栈或寄存器
  保存）+ `mov` + `ret`，且 getter 结果通常被迫落 temp（StackFold 对 CallExpr 强制
  temp 化，StackFold.cs:399-424），阻断常量传播/CSE。
- 折叠后：单条 `mov reg, [obj+offset]`（getter）/ `mov [obj+offset], reg`（setter），
  且表达式留在原地可继续参与调用方折叠（如 `obj.X + 1` 直接折叠为
  `obj->X_f + 1`，铁律 2f-2 最大化表达式深度）。

结论：折叠在热路径（循环内属性访问、装箱前读取等）是数量级差异，
正是铁律 2j"不要把这类当成需要编译为函数的东西，影响性能"的语义。

## 2. 形态判定（解码验证）

判定对象：**每个方法体**（非抽象、RVA≠0 的方法，MethodBodyReader 能读出
IlBytes 的方法）。判定输入用 `IlDecoder.DecodeMethod` 产出的指令序列
（与 StackFold 同源），**不用猜测/正则**——铁律 2j 条件③。

### 2.1 实例 getter（精确形态）

```
[0] Ldarg_0            （或 Ldarg/Ldarg_s 操作数=0 —— 解码器两种编码都接受）
[1] Ldfld  token       （token 解析 → 声明类型 Owner + 字段名）
[2] Ret
```

长度 = 3 条指令。可放宽：getter 前允许 `nop`（调试构建）。

### 2.2 实例 setter（精确形态）

```
[0] Ldarg_0            （this）
[1] Ldarg_1 / Ldarg_s 1（value）
[2] Stfld  token
[3] Ret
```

长度 = 4 条指令。setter 的 `Stfld` 弹栈顺序：value 在栈顶、this 在下
（与 StackFold.cs:167-184 的 `Stfld` 处理一致）。

### 2.3 静态属性

```
getter: Ldsfld token; Ret        （2 条）
setter: Ldarg_0; Stsfld token; Ret（3 条）
```

### 2.4 判定实现

```csharp
// 新文件 src/il2cppc/Emit/AccessorAnalyzer.cs（仿 VTablePlanner 的预扫描 pass 风格）
// 输入：解码后的 IlInstruction 序列 + 方法信息（IsStatic/IsVirtual/IsOverride）
// 输出：FoldedAccessor { bool IsGetter; bool IsStatic; string FieldCppName;
//                       string OwnerFullName; bool FieldIsRef; bool FieldIsVolatile }
// 判定规则：指令数与 opcode 精确匹配；Ldfld/Stfld token 经 md 解析
// 字段声明类型（FieldToken → OwnerFullName，同 StackFold.cs:926-928 的
// ResolveField 路径）；token 无法解析 → 不折叠（保守）。
```

判定不变量：**形态不匹配一律不折叠**（落入普通 call 路径），绝不部分匹配。

## 3. 折叠安全条件（全部满足才折叠）

| # | 条件 | 检查点（真实代码） | 说明 |
|---|---|---|---|
| ① | 非虚 | `MethodDef.IsVirtual` / `IsOverride`（src/il2cppc/Model/MethodDef.cs:35-36，VTablePlanner 已据此入虚槽） | virtual/override 走 vtable 分派，折叠破坏多态（铁律 2j 原话） |
| ② | 字段在同类内 | `Ldfld/Stfld token` 解析出的 OwnerFullName == 方法声明类型 FullName | 跨类型字段访问不可折叠（基类私有字段 setter 语义、可见性差异） |
| ③ | 体确认为简单 accessor | §2 精确形态判定 | 形态之外（有 if/null 检查/计算）一律不折叠 |
| ④（建议补充） | 字段非 volatile | `FieldDef` 属性（volatile 字段的 get/set 有 acquire/release 语义，折叠成普通访问丢失内存模型语义） | 铁律 2j 未列出，但语义正确性要求；volatile 字段标注后不折叠（现阶段模型无 volatile 标注，字段默认非 volatile，条件自动满足——文档化留口） |
| ⑤（建议补充） | 不破坏显式接口实现/属性接口 | getter/setter 若实现接口属性方法（InterfaceImpl 映射），折叠后接口调用仍走 vtable 槽（函数仍发射），调用点折叠不影响接口槽 | 见 §4.3 方法保留策略 |

## 4. 实现要点（转译器：位置与改动）

### 4.1 推荐：两层结构——预扫描 pass + StackFold 调用点折叠

**为什么在 StackFold 折叠（而不是 CodeGenerator 发射层）**：

1. 折叠对象是 IR 表达式（`FieldExpr` / `FieldAssignStmt`），这两个 IR 节点
   已是第一等公民（StackFold.cs:149-184 的 Ldfld/Stfld 分支直接构造，
   CodeGenerator 已有完整发射路径，含 IsRefField 类型推断与 GC 根注册）。
2. 折叠发生在 CallExpr 创建**之前**（StackFold.EmitCall，StackFold.cs:516-641）：
   折叠后不产生 temp、不产生函数名解析，发射层零改动（CodeGenerator 的
   `EmitFunctionName` / `EmitTask9Call` 根本不看到这个调用）。
3. 形态判定需要 IL 字节——StackFold 流程内 `IlDecoder` 已解码（CodeGenerator.cs:153），
   预扫描 pass 复用同一解码结果（避免二次解码）。
4. 发射层折叠的缺点：CallExpr 已带参数/this，发射层只能"改写函数名为字段表达式"
   ——但 CallExpr 是表达式，setter（语句形态）无处安放；且发射层折叠绕过了
   StackFold 的栈语义（this 弹出时机），容易引入求值顺序错误。

### 4.2 具体改动点（按文件）

**新增文件 A：`src/il2cppc/Emit/AccessorAnalyzer.cs`**

```
public sealed record FoldedAccessor(
    bool IsGetter, bool IsStatic, string FieldCppName,
    string OwnerFullName, bool FieldIsRef);

public static class AccessorAnalyzer
{
    // 预扫描：对每个方法（非抽象/有体/PInvoke 排除），解码并判定形态。
    // 产出 Dictionary<int methodToken, FoldedAccessor>。
    public static Dictionary<int, FoldedAccessor> Scan(
        PEReader pe, MetadataReader md, IReadOnlyList<TypeDef> types);
}
```

- 判定逻辑按 §2 形态表实现；`Ldfld/Stfld` 字段 token 解析复用
  StackFold.cs:973 的 `ResolveField` 路径（统一解析，不重复实现）。
- **只判定 `get_*` / `set_*` 前缀方法**（C# 属性访问器命名约定；非此前缀的
  同形态方法不折叠——方法名必须是属性访问器，避免误折叠普通方法
  （如 `int GetX() { return _x; }` 形态相同但语义上仍是方法，折叠它虽
  语义等价但会破坏 ldftn/委托/反射可见性，保守不折叠）。

**改动点 B：`src/il2cppc/Ir/StackFold.cs`**

1. `Fold` 签名扩展（与既有 `md`/`types` 可选参数同风格，保持测试兼容）：
   ```csharp
   public static List<Stmt> Fold(List<IlInstruction> il, MethodContext ctx,
       MetadataReader? md = null, IReadOnlyList<TypeDef>? types = null,
       IReadOnlyDictionary<int, FoldedAccessor>? accessors = null)
   ```
2. `EmitCall`（StackFold.cs:516）在 `MethodRefResolver.Resolve` 之后、
   弹参之前插入折叠判定：
   ```csharp
   var resolved = md != null ? MethodRefResolver.Resolve(...) : null;
   if (md != null && accessors != null
       && accessors.TryGetValue((int)ins.Operand, out var acc))
   {
       return EmitFoldedAccessorCall(stmts, stack, temps, ins, resolved, acc);
   }
   ```
3. 新增局部函数 `EmitFoldedAccessorCall`：
   - getter（实例）：`this = stack.Pop()` → `Push(new FieldExpr { Object = this,
     FieldCppName = acc.FieldCppName, OwnerFullName = acc.OwnerFullName,
     IsRefField = acc.FieldIsRef, IsValueTypeObject = … })`（复用 Ldfld 分支同款
     FieldExpr 构造，StackFold.cs:150-158）。
   - setter（实例）：`value = stack.Pop(); obj = stack.Pop();` →
     `stmts.Add(new FieldAssignStmt { … })`（复用 Stfld 分支同款构造，
     StackFold.cs:172-183）。
   - 静态 getter：`Push(new StaticFieldExpr { FieldName = … })`（复用 Ldsfld
     分支，StackFold.cs:144-145；注意静态 getter 仍需 `EnsureCctor`
     守卫语义——ldsfld 路径已有，复用）。
   - 静态 setter：`value = stack.Pop()` → `AssignStmt`（复用 Stsfld 分支，
     StackFold.cs:146-148）。
   - 值类型（struct）接收者：this 可能经 `Ldloca/Ldarga` 传地址
     （LocAddrExpr）——FieldExpr 的 `IsValueTypeObject` 与 LocAddrExpr
     路径已支持（StackFold.cs:156, 125-134），getter 折叠后生成
     `(&loc)->f` / `.f`（CodeGenerator 既有发射处理），setter 同理。
   - **setter 返回值注意**：C# setter 是 void，ResolvedMethod.ReturnsValue=false，
     折叠后不发 Push（不产生 temp）——与既有 void call 分支行为对齐。

**改动点 C：`src/il2cppc/Emit/CodeGenerator.cs`**

1. `Generate`（CodeGenerator.cs:100 附近，vtable 规划 pass 之后）加一行预扫描：
   ```csharp
   var accessors = AccessorAnalyzer.Scan(pe, md, types);
   ```
2. 方法体折叠调用处（CodeGenerator.cs:154-159）传入：
   ```csharp
   var stmts = StackFold.Fold(insns, ctx, md, types, accessors);
   ```
3. **方法发射策略**（CodeGenerator.cs:134-181 的方法循环）：
   - 被折叠的 accessor 方法：**默认不发射独立函数**（铁律 2j：不编译为函数）。
     实现：折叠判定在预扫描期完成，方法发射循环跳过
     `accessors.ContainsKey(token)` 的方法（同时跳过 generated.h 声明）。
   - **保留场景**（未来 M3 反射/委托/序列化保留清单命中时，铁律 2j + 2g-2）：
     保留清单（动态入口分析产出）要求该方法可寻址（ldftn 委托绑定、
     反射 GetValue/SetValue、序列化）→ 此时**函数发射但调用点仍折叠**
     （性能路径不受影响，函数仅作为可寻址符号存在）。M4 阶段无反射，
     直接采用"不发射"策略；保留清单驱动在 M5 分析器落地时接入。

### 4.3 边界情形清单

| 情形 | 处理 |
|---|---|
| 属性被 callvirt 调用（多态） | 安全条件①拦截：virtual 属性不折叠（不进入 accessor 表） |
| 属性经接口调用 | 接口属性必虚（abstract/virtual），不折叠 |
| 自动属性（`{ get; set; }` + `[CompilerGenerated]` 后备字段） | 正是标准形态，折叠生效（最大受益场景） |
| getter 带 null 检查（`get { return _f ?? …; }`） | 形态不匹配，不折叠 |
| 调试构建（nop 前导） | 允许 nop 前缀（判定容错），仍折叠 |
| 泛型类型属性 | 实例字段布局 per 特化，FieldCppName 按实例类型解析；泛型共享代码
  （引用类型实参）字段偏移一致——按既有 FieldExpr 路径自然支持 |
| volatile 字段 | 建议条件④：标注 volatile 的字段不折叠（当前模型无此标注，自动通过） |
| 索引器（`this[int]`） | 形态不符（参数不止 value），不折叠 |
| P/Invoke/抽象/接口方法 | RVA=0 无体 → 预扫描跳过（AccessorAnalyzer 判 RVA≠0） |

## 6. 性能影响评估

| 场景 | 不折叠（现状） | 折叠后 |
|---|---|---|
| `for` 循环内读属性 | 每迭代 1 次 call+ret + temp 落栈 + NOINLINE 屏障 | 1 条 mov，且 `obj.X < n` 整体保留为寄存器比较 |
| 链式访问 `a.B.C` | 3 次调用，3 个 temp | 3 次 mov（优化器可 CSE 公共基址） |
| setter 写入 | call + 参数传递 | 1 条 mov |
| 代码体积 | 每属性 1 函数（含 NOINLINE 序言/帧记录代码） | 零代码 |

风险点：折叠后字段直接暴露——**C++ 编译器可能跨语句提升/合并字段访问**，
只要不改变 .NET 内存模型语义（非 volatile）即安全；volatile 场景按
条件④排除。装箱/拆箱路径的 box 字段读取（Box_int32 payload）不适用折叠
（box 类型无属性方法，天然安全）。

## 7. 与 JIT 预留的关系

属性折叠是**转译期优化**：JIT 阶段同样适用——JIT 编译器（IR→机器码后端）
在 IR 层做同一形态判定（accessor 折叠是经典的编译器优化，与 AOT 共用
AccessorAnalyzer 的判定逻辑，判定器未来提取为共享组件）。因此本设计
不阻塞 JIT：折叠只发生在编译端，运行时零感知（docs/architecture/jit-预留.md
不涉及运行时改动）。
