## 0. 项目本质（用户原话澄清，最高优先级）

> "这是要把 IL 转译成对应的 C++ 代码来跑起来，比如 `ldarg.0 ldarg.1 add stloc.0` 这个 IL 指令对应 C++ 代码应该是 `局部变量0 = 参数0 + 参数1`。"

**铁律 1 — AOT 静态转译，绝不做解释器：**
- 每个 IL 指令序列必须被转译为**等价的静态 C++ 语句**，由 C++ 编译器生成原生机器码运行。
- 示例对照（验收基准）：
  - `ldarg.0; ldarg.1; add; stloc.0` → `loc0 = arg0 + arg1;`（先折叠成 IR 表达式再发射）
  - `ldc.i4.5; stloc.0` → `int32_t loc0 = 5;`
  - `call` → 直接 C++ 函数调用；`newobj` → `il2cpp_object_new` 分配 + 构造调用
- 转译产物必须是**可读、可审计、可再生**的 C++ 源码（*.cpp/*.h），由 MSVC/MinGW/WSL GCC 编译。
- 禁止任何"运行时逐条解释 IL"的实现路径。M7 解释器兜底 ≠ 解释性语言：它是 AOT 主路径之外、用于元数据/动态场景的辅助（且不含 Emit），主执行路径永远是转译后的静态 C++。

**铁律 2j — 性能优先 + JIT 预留 + 属性折叠（用户原话，2026-08-03）：**
> "必须保证极高性能，然后必须支持后续JIT部分，就是未来要能支持用户动态编程，目前是暂定计划，先推进aot编译器本身，然后属性优化，有的属性只是直接设置返回字段值，不要把这类当成需要编译为函数的东西，影响性能。"

- **性能是最高优先**：AOT 转译产物的执行性能必须达到极致（对标 IL2CPP 水平）。任何设计决策权衡时性能优先。
- **JIT 预留（架构方向，暂定计划）**：未来支持用户动态编程（运行时动态编译/加载代码）。当前专注 AOT 编译器本身，但**设计不得堵死 JIT 路径**：① 方法调用经函数指针表（可替换/可插桩）；② 类型描述符可扩展（运行时类型注册已有）；③ 内存分配走运行时分配器（GC 已知）；④ 元数据（方法/签名）运行时可达（M4 导出表 + 类型注册是第一步）。每次架构决策需自问：JIT 时代还能工作吗？
- **属性折叠（accessor inlining）**：简单属性——get 体仅 `ldarg.0; ldfld f; ret`、set 体仅 `ldarg.0; ldarg.1; stfld f; ret`——**不得编译为函数**（避免调用开销，性能优先）。转译时把属性访问点直接折叠为字段访问。**折叠安全条件**（必须全部满足）：① 属性方法非虚（virtual/override 的多态分派不能折叠）；② 字段在同类内（跨类型字段访问不变）；③ 方法体确认是简单 accessor 形态（解码验证，不是猜测）。属性折叠是转译期优化——纯 AOT 安全，不破坏任何语义。

**铁律 2e — 生成代码性能（用户原话，2026-08-02 追加）：**
> "我们还要保证生成出来的 C++ 代码执行效率极高，如果代码效率太低了还不如官方 JIT，那我们所有的努力全部白费了。"

- **性能定位**：AOT 产物性能必须 >= 官方 .NET JIT（Release）——原生 C++ 无解释器/无 JIT 编译期开销、编译器全程序优化空间更大，理应达到或超过；达不到 = 项目失败。
- **零开销抽象**：栈折叠直接生成表达式（不做逐指令模拟）；常量折叠在生成期完成（int32 回绕已实现）；临时变量最小化；无运行时类型分派（除虚方法/接口语义本身所需）；无每次调用的元数据查找（调用目标编译期确定）。
- **编译期决策**：凡能静态确定的（方法目标、字段偏移、类型判定、常量运算）一律编译期定死；运行时只保留 .NET 语义真正要求的动态行为（虚分派/接口分派/GC/异常/反射）。
- **内联机会**：生成代码是常规 C++ 源码，MSVC/MinGW/WSL 的优化器（-O2）对跨函数内联/常量传播完全开放；不得生成阻碍优化的构造（过度的 volatile、间接跳转、动态分配热路径）。
- **性能回归保障**：M6 起建立性能基准（与官方 .NET 对比的 micro-benchmark 套件），关键路径（整数运算、循环、对象分配、字段访问、虚调用、字符串）逐项对比，回退即失败。
- 效率约束贯穿每行生成代码与运行时：**每处设计都问"这个开销官方 JIT 是否也要付？如果不付，我们为什么付？"**

**铁律 2f-2 — 为什么必须理解 IL 语义（用户原话，2026-08-02 追加）：**
> "为什么一定要真正理解IL这些逻辑呢？是因为如果不理解我们不能正确翻译代码表达式哦，该括号的时不加不改的乱来，而且我们还要利用CPP编译的编译器优化，寄存器优化这些，否则性能根本就起不来，纯栈上操作是不可能获得高性能的输出的。"

- **语义 → 表达式正确性**：理解 IL 的根本目的是把指令序列**正确翻译成 C++ 表达式**——运算符优先级/结合律、括号的位置、求值顺序、类型转换，一处乱来就产生错误代码。每个 IL 二元/一元运算都必须映射为带精确括号的 C++ 表达式（我们 CodeGenerator.EmitExpr 的括号策略：BinaryExpr 必带括号、常量折叠时剥除、EmitCondition 避免双重括号——均为此服务）。
- **性能路径 = 表达式，不是指令模拟**：高吞吐代码必须折叠成**大表达式树**交给 C++ 编译器（-O2）做寄存器分配、常量传播、公共子表达式消除、内联。逐条指令落临时变量的"伪栈模拟"生成物（每 opcode 一个 temp + 一条赋值）只能得到栈机级别性能——**禁止**。
- **检查基准**：生成代码审查时问——"这段 C++ 是否与手写等效 C++ 一样能被优化器处理？是否有不必要的临时变量/间接层/volatile 破坏了优化？"
- StackFold 的使命（铁律化）：**最大化表达式折叠深度**（ldc/ldarg/ldloc/算术/比较/字段读 → 单表达式），仅当控制流/副作用强制时才引入临时变量（call 结果、join 槽、快照）。

**铁律 2g — 泛型展开（用户原话，2026-08-02 追加）：**
> "对于模板类生成，我应该给你说的很明白，我们不能翻译成 C++ 的 template <.....> 这种形式哈，这会代码膨胀，而且这样我们很难去弄 T 的问题，编译器限制"

- **禁止 C++ template 生成**：泛型类型/方法绝不允许转译成 `template <typename T> ...` 形式。理由（用户明确）：
  1. **代码膨胀**：C++ template 由 C++ 编译器在每翻译单元实例化，重符号/重复实例化/ODR 冲突难以控制；
  2. **T 的问题**：C++ 模板对 T 的约束（C# 泛型约束、引用/值类型语义差异）无法用 C++ 模板机制精确表达（C# 泛型是运行时可识别类型的，C++ 模板是编译期文本替换）；
  3. **编译器限制**：三编译器（MSVC/MinGW/GCC7.5）模板实例化行为差异、编译时间爆炸。
- **正确方案（IL2CPP 同款）**：**编译期泛型实例化（monomorphization/closure）**——分析器枚举全部泛型实例（List<int>、List<string>...），每个实例生成一个**独立的普通 C++ struct**（`List_int` / `List_String`...）与独立方法函数，类型参数在生成期替换为具体类型。静态类型系统完全闭合，运行期零泛型开销。
- **T 的约束处理**：泛型参数的约束（where T : class / struct / new() / 接口）在分析器侧验证；约束检查编译期完成（闭合世界证明），运行期不做泛型约束运行时检查。
- 与裁剪（L1 默认）正交：实例集 = 静态可达 ∪ 动态保留清单。

**铁律 2g-2 — 反射能力（用户原话，2026-08-02 追加）：**
> "反射是可以调用函数，设置属性，设置字段这些的哦。你必须要正确实现，好好记住。"

- **反射 = 完整运行时操作能力，不是只读查询**：
  - **调用函数**：`MethodInfo.Invoke(instance, args)`——任意方法（实例/静态/私有/泛型实例）经统一 Invoker 动态调用 ABI 执行（零 JIT，M3 反射体系）
  - **设置属性**：`PropertyInfo.SetValue` / `GetValue`——setter/getter 访问器经反射调用（含索引器）
  - **设置字段**：`FieldInfo.SetValue` / `GetValue`——实例/静态字段经反射读写（含 GC 引用字段，值经 box/unbox 传递）
  - 构造函数反射实例化：`Activator.CreateInstance` / `ConstructorInfo.Invoke`
- **实现路径**（spec 4.4/6.3 动态运行时域）：编译期封闭世界分析 + 元数据表静态固化 + 统一 Invoker（方法句柄 + 参数数组 marshalling）——所有反射目标在编译期预编译进保留集，运行期只查表不生成代码。
- **验证标准**：反射 e2e 用例必须能 `Invoke` 用户方法、`SetValue` 字段/属性并观察到程序行为变化——与直接调用/直接赋值结果一致。
- 此铁律写入 memory.md（方法论）与后续 M3 计划——实现反射时不得退化为"只读元数据查询"。
